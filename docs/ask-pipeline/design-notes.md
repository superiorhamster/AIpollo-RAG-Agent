# Ask provenance and follow-up design notes

These notes preserve the baseline findings and proposals that preceded history-aware Ask. The [current architecture](architecture.md) describes what the worktree implements, including retrieval rewriting, separate conversation claims, and manual Retry.

## How the baseline attached citations

1. Retrieval returns a server-generated chunk UUID and its authorized document name/ID, page, region, text and score. The worker packs passage ID, section and text alongside the current objective and, when present, up to six earlier succeeded user questions. The system prompt tells the model to use supplied evidence only and treat prior chat as untrusted data. See `services/retrieval-service/app/search.py:129`, `services/agent-orchestrator/app/worker.py:16`, `:108`.
2. The model chooses each claim’s text and evidence UUIDs. `GeneratedAnswer` validates the shape, and `Claim` requires evidence IDs. The worker drops claims with unknown or unpacked IDs or mismatched required structured fields. For accepted IDs it copies metadata from Retrieval. It does not check that the passage supports the proposition or every part of a compound claim. See `services/agent-orchestrator/app/types.py:75`, `services/agent-orchestrator/app/worker.py:158`.
3. The browser renders the returned claim and pills, filtering pills against listed document IDs. Each pill uses the server name and page and points the reader at the supplied document, page and optional region. This is navigation over an existing attribution. See `apps/web/app/workspaces/[workspaceId]/interaction-panel.tsx:286`, `apps/web/app/workspaces/[workspaceId]/document-shelf.tsx:278`.

For a label absent from the PDF but available in the chat input, the earliest likely bad association is **generation**, when the model emits a chat-derived proposition paired with an otherwise valid passage UUID. The validator accepts that ID by membership. A separate class of incorrect citations could start earlier if parsed page or region metadata is wrong. Distinguish the two by comparing the persisted claim against the exact stored passage and then comparing that passage against the PDF.

## Observed mixed answer

The [setup notes, §8](../../../aipollo-setup-gemini-debug.md#8-ask-và-kiểm-tra-ngữ-cảnh-nhiều-lượt) and the reported case record that the user introduced “Mật mã Mây Tím” in chat. A later same-chat question returned that label and 16:10 Friday, attributing both to the PDF. The PDF supports the time. The label came from the conversation. This is consistent with prior user questions entering the answer prompt and a valid document UUID being reused for a chat-derived claim. It does not demonstrate retrieval-query rewriting, prior assistant answer loading, or a separate chat-memory subsystem. The earlier history-only turn raised `interaction_unavailable`; its precise cause remains unknown. A history-only question with no retrieval hits would ordinarily abstain before chat, and with hits could still fail in generation or validation.

## Options and acceptance checks

| Option | Design and tradeoffs | Acceptance checks |
|---|---|---|
| Typed per-claim provenance | Give document and chat evidence distinct namespaces and types, such as `document_chunk` and `user_turn`. Validate chat turn IDs against the same authorized conversation, document IDs against packed scoped chunks, and prefer atomic claims for mixed answers. Render PDF pills only for document support and “From this chat” for user-supplied context. Identity validation is deterministic, but reliable semantic attribution still requires additional checks. Migrate consumers of the saved claim schema, including artifacts. | Time receives its PDF pill; label receives only an authorized chat marker. Reject foreign chat IDs and unknown/unpacked chunks. Clicking the time pill opens the correct page. Saved/exported answers retain provenance, and legacy records remain readable. |
| Separate source-grounded and chat-context answer sections | Use independent structured outputs or answer passes, with a document pass that receives no history facts and a chat pass that can cite only authorized turns. This reduces leakage between sources and makes abstention easier to explain. Extra calls add cost, latency and potential disagreement; routing alone can misclassify mixed questions. | Mixed question returns both facts in the correct sections. Prompt snapshots prove the document pass never receives the invented label. History-only turns make no document claim. A mismatch never silently adds a PDF pill to the chat section. |
| Verify document attribution before rendering | Require a quoted span from the claimed chunk, verify quote membership, and optionally use a separate entailment check to accept, split, flag or drop claims. Exact quote checking is cheap and auditable but does not prove paraphrases or logical entailment. Model-based verification adds latency and can make errors itself. | Reject a real chunk ID paired with the unsupported label; accept a grounded time paraphrase with matching passage; flag compound claims where only part is supported. Report false accepts and false rejects on labeled examples. |
| Rewrite retrieval queries for follow-ups | Use bounded authorized history to resolve references into a standalone search query, preserving the original question for the answer stage. Keep the same selected-document ACL and generation filter before and after rewriting. Track original/rewritten query and retrieval metrics in safe test traces. Rewriting can increase recall, but adds latency and may drift or inject chat-only facts. Skip or fall back to the original query when resolution is uncertain. | “When was that watering?” retrieves the expected passage in context; new chat asks for clarification when the referent is missing. A unique label invented in chat is not treated as a document fact or required document keyword. Compare Recall@k, attribution accuracy and latency with and without rewriting. |
| Explicit chat-only response or clarification | Detect requests about the current conversation and answer from allowed user turns with a chat marker. Supply no PDF pill. If the user has no applicable prior turn, say the detail was not found in this chat. Distinguish chat-only recall from source evidence absence and from execution failures. Supporting zero selected sources for this path requires changes to UI and API source validation. Explicit mode is easier to reason about; automatic routing reduces friction but can misclassify. | Same chat recalls the label with no PDF pill; New chat cannot recall it with the same selected PDFs; a user's separate chat and another user's conversation are never loaded. Genuine provider failures remain visibly distinct from unavailable history. |

[Debugging notes](debugging.md#observations-and-open-hypotheses) identify likely matching runs and show HTTP 200 even for the failed run's completion boundary. Confirm the mapping to the UI turns and capture active source generations, the exact validation error, and a redacted or synthetic trace of packed passages and emitted IDs. Evaluate the same-chat/New chat comparison before attributing the failure to follow-up handling. If a future version expands history, keep user-authored notes distinct from prior assistant outputs and require independent support for factual claims.
